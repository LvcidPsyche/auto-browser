# Decisions

- 2026-09-20: The browser runtime, controller, and MCP broker run on the existing Hetzner server. Start with one active browser; extra isolated browsers are capacity planning only.
- 2026-09-20: The owner enrolls a phone authenticator and supplies one fresh code to open each new browser session. The assistant never receives a phone code or opens a session. It may use the already-open owner session through its separate bearer credential until the owner closes it; no per-task code or arbitrary task timer.
- 2026-09-20: Closing a local viewing tab is not the same as closing the server browser session. The owner must explicitly close the server session to revoke assistant access and require a fresh code next time.
- 2026-09-20: Do not publicly expose raw noVNC, VNC, controller, or broker. A server-side assistant needs a private network path. Remote owner access from a phone/browser needs a separately authenticated HTTPS portal; this is not yet deployed.
- 2026-09-21: Hermes is connected to the private broker on the existing server through a dedicated internal Docker network and its own named bearer. MCP initialization and tool discovery passed. Agent actions remain denied until a human opens a TOTP-verified browser session.
- 2026-09-21: The owner clarified the intended later product flow: each user supplies and verifies their own email on first use, has isolated browser data, and the connected assistant guides setup and resumes automatically when the user finishes a sensitive step. Do not publish the staged single-owner email-allowlisted gateway as though it implements that multi-user requirement. Identity verification, enrollment policy, per-user storage/runtime isolation, and user-scoped agent grants must be implemented first.
- 2026-09-21: Enrollment is invitation-only, by the owner. The browser MCP is a reusable connector for Hermes, Codex, Claude, and an optional advanced Social Operator capability; it must not rely on a shared global agent secret or let an LLM choose another user's profile. Current live wiring is only to the `hermes` container in the `hermes-stack` Compose project on the server; external connectors are not yet deployed.
- 2026-09-21: The owner wants any MCP-capable assistant to perform ordinary browser actions after he connects it and opens the human-verified session; passwords, email/app codes, and human-verification challenges remain human steps. Deployed broker now has a safe `browser.session_status` MCP tool, session-generation-bound grant reuse, and owner revocation that waits for in-flight actions and blocks later actions. Live MCP discovery and unconfigured-TOTP denial passed. The public portal and OAuth-protected remote MCP URL remain undeployed; no claim that Codex/Claude are connected. Existing browser login cookies are not automatically saved on close; explicit owner auth-profile save/reopen is required until an encrypted owner-bound autosave design exists.
- 2026-09-21: The owner will not connect any assistant over the private SSH-tunnel path. No assistant is connected until the browser service is publicly deployed behind an authenticated HTTPS portal and a user-scoped OAuth-protected MCP endpoint. Treat the local loopback/tunnel route as an internal test path only; delivery target is the public deployment, which still requires invitation/identity, per-user isolation, and OAuth authorization to land first.
- 2026-09-21: Connection UX is a hard product requirement, not a nice-to-have. The owner must never copy, paste, store or configure a bearer token, secret or config file to connect an assistant. The only things he ever handles are (a) one public URL pasted into the assistant once, and (b) a short one-time code he receives and types into the portal page in his own browser. Everything else — authorization, credential minting, storage, renewal and revocation — happens server-side behind per-user OAuth. Any design that requires the user to obtain or paste a token is rejected, including the current named-bearer path, which is an internal test path only. After that single approval the assistant stays connected and can perform ordinary browser actions without a further code, until the user explicitly disconnects it or closes the session.
- 2026-09-21: Public ingress is solved by the existing stack; no new certificate or DNS work is needed. `dokploy-traefik` (traefik v3.6.7) terminates 80/443, routes by Docker labels on `dokploy-network`, and already holds a wildcard `*.fareeqk.com` certificate from the `letsencrypt-dns` resolver (Cloudflare DNS challenge, storage `/etc/dokploy/traefik/dynamic/acme-dns.json`). The two new hostnames are published by adding router labels exactly as `hermes.fareeqk.com` does. Because portal and MCP authentication is our own email-code + per-user OAuth, Cloudflare Access is no longer part of the design and the earlier Cloudflare Access token limitation is no longer a blocker. Traefik must route only to the portal and the OAuth-protected MCP resource, never to the raw broker, controller, noVNC or VNC ports, which stay loopback-bound.
- 2026-09-21: Authenticator codes replace email codes on the whole daily path. Rationale: TOTP needs no email provider, no deliverability, and no waiting; a compromised mailbox no longer grants browser access; and the owner's required UX (one link, one short code, done) is satisfied identically and faster. Email is demoted to an optional recovery contact only — never a login factor and never a second factor. Enrollment happens at the single-use invitation link: the invitee sets a display identity, enrolls an authenticator by confirming one generated code, and receives one-time recovery codes shown exactly once and stored hashed. Portal login and browser-session opening both use an authenticator code; a used code cannot be replayed. Losing the authenticator is recovered by a recovery code or by the owner issuing a fresh invitation, never by email alone.
